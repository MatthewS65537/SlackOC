# OpenCode V2 and Slack responsiveness

SlackOC requires OpenCode **2.0.12 or later in V2**. It uses the generated
`@opencode/client` API and the local service's discovery/authentication flow.
Each project has an explicit location; projects share one event subscription.
Stopping SlackOC or using `\restart` does not stop OpenCode or another client.

## Questions and permissions

Permission cards use Slack buttons. Questions use a bounded, one-field-at-a-time
card with option buttons, multi-selection, and a native free-text modal.
Long option lists are paginated. V2 option values and field keys are preserved;
typed values and conditional fields are converted to the V2 form contract.

Question answers, delivery identities, and in-flight uncertainty persist across
bridge restarts. Duplicate submissions are locked. After an ambiguous reply,
**Retry submission** checks whether the form is still pending before another
explicit submission. Use **Edit answers** for validation failures, or
`\questions` to recover cards and inspect thread/DM delivery status.

The Slack app must have Socket Mode and interactivity enabled, as specified by
`manifest/slack-app-manifest.json`. If a modal fails to open, SlackOC reports the
failure through the action response; try **Type your answer** again.

## Latency and recovery

- Receipt reactions start before attachment downloads.
- Prompt admission does not wait for a Slack status post or queued message.
- Warm project handles do not run synchronous health probes or model “ping” prompts.
- Slack posting retains per-channel pacing. Updates, history, and uploads use
  separate method lanes; a 429 delays only the affected method across channels.
- Progress moves below newly emitted content by posting/adopting a replacement,
  then deleting the old message. Overlapping moves coalesce; queue pressure and
  bounded retry backoff can temporarily delay repositioning.
- Reconnection reconciles durable server evidence. An uncertain prompt is never
  automatically retried solely because a network request failed.

Sub-second **warm prompt admission and receipt feedback** are performance goals,
not a promise of a complete model answer in less than a second. Slack rate limits,
attachments, cold service startup, and model generation have separate costs.

## Verification

```sh
npm run check
npm test -- --maxWorkers=4 --minWorkers=1
npm run build
npm run smoke -- --no-model # live forms/permissions, temporary session cleaned up
npm run smoke              # also runs two tiny model turns and reports admission time
```

The smoke test uses the installed service and configured provider. It does not
measure Slack end-to-end latency. Validate native button clicks and modal
submission in a signed-in Slack client after starting the rebuilt bridge.
